Coldworks design reference

Coldworks keeps one record of what a repository's people and agents decide, grades each decision by what happens after it merges, and turns work that keeps holding into a brief, a recipe, or a check that runs without a model.

The thesis is to use AI to reduce AI: compile repeated agent work into deterministic artifacts, and prove each one by the model calls it removes. The lead number is T, the share of decisions a model still makes. A falling T means the product is working.

This page describes the design as it stands on 2026-10-26. Most of it is designed, not built. Every item carries one of these statuses:

Vision

Agent work repeats in three ways. Each kind has a hot form that a model performs every time and a cold form that runs without a model after the record shows it keeps holding.

LookingDoingJudging
Hot formRe-reading files, re-deriving settled decisionsRe-constructing an accepted multi-file changeA model read of every instance
Cold formThe brief at session start; the never-reopen pushA recipe: typed, bounded, replayed, signedA check: CEL eligibility, declares what it enforces
BarBeats token-matched context stuffing and a committed AGENTS.mdNet savings against a strong baseline, measured prospectivelyReplay on history, paired mutations, a holdout error bound, a signature
DeoptA contradicting commit demotes the record to contestedUnfamiliar work returns to the agentA miss deopts the check

The measurements set the build order. Navigation is the largest share of agent context on every corpus measured: 41.6% on SWE-agent and 54.9% to 60.3% on Claude Code. Repeated judgment is rare: 0.97% of context on one developer's 1,291 Claude Code calls. So the build goes looking first and judging last.

Five rules of the experience

  1. Nothing to file. You never enter a decision or approve a memory. A commit is the only way to tell the product anything.
  2. Nothing to read unless it changes what you do next. You get one line at the moment it matters, with the evidence one click away.
  3. Nothing to configure. One command installs the hook, and the record is files in your repository.
  4. A number is honest or absent. Every figure has a denominator and a provenance. If a figure can't be computed, you see why, never a zero.
  5. It is yours. Cold artifacts run in your own CI. Cancelling never changes a check's status.

Dependency direction

The spine owns the records and everything else reads them. Imports run spine, then engine, then local and reviews. The store holds no model client, so a model swap is never a store release. Replay in engine/ makes no network call. The layers check enforces all three rules at merge.

Deployment

Clouds at launch are AWS, GCP, and DigitalOcean. The Go SDK reaches the first-party API, Amazon Bedrock, Claude Platform on AWS, and Google Vertex AI, so a customer can use their own model endpoint. A parity spike on 2026-10-19 found no blocker across the five launch transports; no live call was made.

The repository never becomes public, because its history holds spine/ and engine/. The open parts publish as a separate public repository at Phase 3.

The four moments

The product is what happens at four moments, all over one record:

  1. Before the agent starts. The brief lists the decisions the session is likely to touch, the recipes available, and stale lines in the agent instruction files. Code selects it from the files at hand and holds it under about 2,000 tokens. A model never selects it, because a model-selected summary scored below no context at all.
  2. While it works. The never-reopen push fires when a session approaches a settled decision's evidence. run on a recipe is the one tool the agent pulls.
  3. At review. Reviews reads the record before the diff. A pull request that crosses a settled decision carries a contradiction section. Nothing blocks.
  4. After the merge. The deriver writes the decision with its spans. Outcomes grade it over 14 and 60 days. The miner clusters repeats, and the engine drafts a check or recipe, replays it on history, and waits for a signature.
Push, never pull. Context reaches the agent through hooks and server instructions. A tool the model calls to ask spends more tokens every time.

Deterministic checks

make check runs gofmt, go vet, the build, go test -race -shuffle=on, and ten repository rules in tools/check. Built

Each rule is decidable from the tree alone, with no model and no network. Each one fails on a planted bad input under tools/check/testdata/bad/, proved by the tool's own tests. A rule that can't be shown to come out wrong isn't added.

Planned additions each wait on something the scaffold lacks: coverage and suppression ratchets need a merge base, allocation budgets need a hot path, determinism of derivation needs the deriver, and a binary size budget needs the first release binary.

The record

The record is one append-only ledger per repository. The only write verb is a commit. A correction, a state change, or a supersession is a new record, never an update. IR v0.3.0 schema built Signature pending

Conceptually, the record holds five kinds of entry:

decisionderived

What was decided, derived from a merged pull request or a committed document, with evidence spans that point at the lines. Never entered by hand.

evidenceobserved

Spans, diff hunks, a model's verdict, and the falsifier that settled a finding.

outcomegraded

Merge and revert, read from git. The adjudicator is a pure function of merge time and the revert map, with no clock and no network. Hotfix detection doesn't exist yet.

cold artifactguard

A recipe or a check, with its qualification report, activation signature, and subtraction.

session linklink

A session joined to the merged commitment it preceded, keyed by a commit trailer. A session's claims stay advisory until a commit corroborates them.

Normative rules

  • Every record is append-only.
  • The store resolves tenant_id and container_id from facts the producer can't forge. A producer never asserts them.
  • Force and links are derived at read time, never stored.
  • Payload schemas are closed per type version. The store parks an unknown version instead of failing it.
  • Idempotency is UNIQUE (tenant_id, idempotency_key), so one tenant can't suppress another's write.

Sources and force

Every record has exactly one source. Force, which says how much a record is to be believed, is a pure function of the source variant and two demotion facts. Only settled governs.

SourceWhat it isHighest force
prA merged pull request, the canonical commitmentsettled
commitA commit that reached the default branchsettled
docA document at HEAD under the repository's merge governancesettled
sessionAn agent session captureadvisory
inheritedA settled record from another repository in the same organizationadvisory
observedA trace, a judgment, or a receipt from an instrumentnone

A session can never be settled by construction. Session text is attacker-writable, so this rule keeps it out of what the reader trusts. An inherited record never changes force. Corroboration mints a new settled record from the inheriting repository's own commit.

Closed vocabularies
Force     settled | advisory | historical | contested
Status    proposed | accepted | superseded
          | deprecated | rejected
Relation  supersedes | session_of | corroborates
          | cites | inherits
Origin    write_time | imported | recovered

Record types

IR v0.3.0 has a closed vocabulary of 15 record types. A registry row is (record_type, schema_version), so registering a new type is additive. The fixtures under spec/fixtures/0.3.0/ cover valid records, records the validator must reject, and reads.

decision

What a repository decided, from one commitment or one session.

input_state · trace · artifact

The immutable state work ran against, one hot-tier run indexed into content-addressed storage, and deterministic content an agent or recipe produced.

judgment · fingerprint · cluster · cluster_claim

A model's or a check's answer to one predicate, its similarity per tenant, and a hypothesized repeat. Frequency alone never moves a cluster's state; a discriminator does.

outcome

What observably happened, joined to the exact input state.

guard · qualification · receipt

A check or recipe's registry entry, every case of its qualification run, and a receipt per dispatched task that names which tier handled each unit.

link · attestation · redaction

A graph edge between records, an in-toto derivation attestation, and a provable delete that keeps the envelope.

Rungs

The product climbs from one engineer to an organization. Each rung adds one sensor and one signature, by the same mechanism: a commitment grades the record, and a signature cools it. Proposed

Future state

The target state is a day months into use. Every figure in it is illustrative. Proposed

  • Day one, before any hook. One command reads your agent's session files, joins them to git, and prints the share of sessions that re-read what an earlier merge settled.
  • Session start. Three lines appear before you type: a settled decision, an available recipe, and a stale instruction line.
  • Mid-session. The agent proposes reversing a settled decision. One line names the decision and its evidence. You say reopen, or the agent drops the change.
  • Pull request. The check run says the change crosses no settled decision and how many review classes checks answered.
  • A teammate's session. Their brief carries your morning's decision, because the merged pull request carried the decision file.
  • A revert. The record flips the decision to contested on its own, and every brief on that service says so the next day.
  • A new repository. It starts with the organization's settled decisions at advisory force. Its first corroborating merge settles each one locally.

Built for scale

The design targets an organization with 2,000 repositories, 50,000 sessions a month, and 200,000 merges a year. It adds no broker, cache, or second datastore until a named Postgres measurement crosses a pre-registered threshold. A load test at that shape runs before the organization rung opens.

What never appears

An inbox, a memory you edit, a dashboard of agents in flight, a dollar figure, a second product name, or a page you have to keep open.

Proposed ideas

The unified-product pass of 2026-10-18 proposes eight additions. None is signed.

Proposed

The session link as the cross-run key

A commit trailer joins each merge to the sessions behind it, across tools, and yields the cross-run re-derivation share.

Gated on the kill bar

The never-reopen push

When a session approaches a settled decision's evidence, the hook pushes the decision, its date, and its status before the model reasons.

Proposed

Recipe and check as twins

A check decides; a recipe constructs. Both sit in one registry, are signed after shadow, and carry a subtraction and a deopt.

Proposed

Looking and doing as brackets

Shown beside T, never a pass condition, so the looking share can fall even where judgment never cools.

Proposed

Organization inheritance

An inherited source capped at advisory. A repository's own commit corroborates it into a new settled record.

Partly built

Session readers first

Readers for Claude Code and Codex make one engineer the first user. Cursor waits on a dependency ruling.

Proposed

Signed derivation attestations

Every derived record carries an in-toto attestation: derived from commits X..Y by tool T at version V.

Proposed

The stale-instruction line

At every session boot, name the lines in CLAUDE.md, AGENTS.md, and .cursorrules that reference code missing at HEAD.

Unproven, carried as gates

Each unproven claim enters the repository as a pre-registered bar with a kill condition, never as a feature. These are the open ones:

  • The density of compilable judgment on an export nobody in-house wrote.
  • The Stage-5 kill bar for the brief.
  • A recipe's net saving against a strong baseline.
  • The cross-run re-derivation share, the never-reopen collision rate, and session reader coverage.
  • A census unit for T's denominator, and for looking and doing.
  • A hotfix detector, and the lift of outcome grading over a plain currency check.

The smallest honest tests

Each test is cheap, has its bar written before it runs, and can come out wrong:

  1. The cross-run key. Correlate sessions to merges. Control: shuffle the assignment and confirm the share collapses.
  2. The collision rate. Count pull requests that touched a settled span without citing it. Bar: at least one per 50 merges.
  3. Reader coverage. Bar: a majority of files from each tool read end to end.
  4. The kill bar. The brief against token-matched context stuffing, a committed AGENTS.md, and the same brief with force hidden. If it fails, the deriver becomes an AGENTS.md generator.
  5. The rung-0 count. Strangers who ran the report and ran it again, at day 30.
  6. Grading's own case. Count reverts that left the cited span unchanged. If that count is near zero, outcome grading buys nothing over a currency check.

What not to build

The stop list binds every rung:

  • No inbox, accept button, or judgment queue. Commitment is the decision.
  • No hosted capture or live watcher of production agents.
  • No dollars or savings claims; findings and the number only.
  • No "knowledge graph" as a product noun. It describes how the record is organized.
  • No pooled source code across tenants, ever. Outcomes might pool, with consent.
  • No learning loop that feeds evidence back into a prompt.
  • No organization inheritance at settled force.
  • No feature without the moment in the experience that it serves.
